Taking apart the G'AIM'E light gun — both halves of it

A ¥13,200 Time Crisis console turned out to ship a hardcoded AES key, no secure boot of any kind, a licensed Namco arcade emulator, and a gun that is secretly a Linux computer with its own camera and 128 MiB of flash. Here is everything we found, including the bits we got wrong.

{{DATE}} · built from commit {{COMMIT}} · github.com/mattkanwisher/gaime_mods

The G'AIM'E TIME CRISIS Lightgun is a small HDMI console made by Tassei Denki, officially licensed by Bandai Namco for the Time Crisis 30th anniversary and launched on Kickstarter in late 2025. It ships as a sealed appliance: you plug in a gun, you plug in a TV, you shoot things. There is no settings screen, no file manager, no network stack, and no way out of the launcher.

I bought the Japanese retail version in Akihabara. This is what was inside it.

Two things made this project unusually productive. The first is that the vendor publishes a 4 GB full firmware image as an unauthenticated download — not a delta patch, the whole system. The second is that there is no secure boot anywhere in the chain, so once you understand the image you can also put things back.

What's in here

  1. The console: a hardcoded key, a homemade flasher, and a root shell
  2. The gun: an absolute-positioning light gun that already works on any PC
  3. What's still open
Method

Everything here came from the vendor's own public download, a USB cable, a $3 serial adapter, and hardware I own. Nothing was obtained from the vendor under NDA, nothing was pirated, and no game data is republished. Where I got something wrong — and I got several things wrong — the correction is in the text rather than quietly edited out.

Part one

The console

01A 4 GB download and a key left in the updater

The update package is a Windows-only vendor tool plus three .dat files. The .dat files start with the ASCII magic GAIMEENC and have a payload entropy of 7.9998 — genuinely encrypted, not merely packed.

The updater, GAIMEUpdater.exe, is a .NET 8 single-file bundle. Extracting GAIMEUpdater.dll from the bundle and decompiling the FirmwareDecryptor class gives away the entire scheme in one screen, including the key:

AES-256-GCM, key hardcoded in the binary:
  2C4B5B4D84F9A5E0E4D4C2F78B6A1D9E0A0B1C2D3E4F5061728394A5B6C7D8E9

Layout:  "GAIMEENC" (8) · version=1 (1) · max chunk (4, LE = 4 MiB) · base nonce (12)
         then repeating { length (4, LE) · ciphertext · GCM tag (16) }

Per-chunk nonce = base nonce with the LE int32 at bytes 8..12 XORed with the
chunk index. No AAD.

Underneath is a plain Allwinner IMAGEWTY image — the standard PhoenixSuit/LiveSuit container, 49 members — so there was no second layer to defeat.

I wrote the encryptor as well as the decryptor, because that is the only honest test of whether you have understood a format. Re-encrypting an unmodified image reproduces the vendor's shipped .dat byte for byte, same SHA-256. At that point the container is not "probably understood", it is solved.

The ODM is Dashine. Every app package is com.dashine.*, and a leftover build path in the config files reads D:\Dashine\New Products\Lightgun\Firmware\GaimeBox_Burn_Tools\. A second leftover dev path (C:\Users\Ian\...) gave away where the updater stages its decrypted image, which is how I confirmed the decryption chain before writing any code.

The three SKUs are the same firmware

The three retail bundles — Basic, Premium, Ultimate — ship three different .dat files, so you would reasonably expect three different builds. They are not.

Basic simply omits three of the four game APKs (though it keeps the odex/vdex stubs for all four). Premium and Ultimate, compared file-by-file across every partition, differ in exactly one file: the launcher APK. Those two launchers share a package name, differ by five bytes, and their only differing strings are compression artefacts.

Which means the Premium-vs-Ultimate distinction is not in the firmware at all. The first-launch "authentication" — Premium wants a pedal, Ultimate wants two guns — is just runtime accessory detection.

The emulator is a licensed Namco core, not MAME

This was the finding I least expected. Each game is a Unity app wrapping a native core, and for Time Crisis that core is libSys22Plugin.so, stamped:

(C)2021 BANDAI NAMCO Research Inc.

So this is an in-house, licensed Namco System 22 emulator — not FBNeo, not MAME. Practically that means there are no GPL obligations to lean on and no source offer to expect. It also means the exported API is unusually clean, and shipped with its debug hooks intact:

Sys22Plugin_SetRom            Sys22Plugin_DebugReadMemory
Sys22Plugin_SetInputPointing  Sys22Plugin_DebugWriteMemory
Sys22Plugin_SetEEPROM         Sys22Plugin_GetForceFeedback
Sys22Plugin_UpdateFrame       Sys22Plugin_Get/PutRankingData

ROM data is handed in via Sys22Plugin_SetRom from the C# layer, so it lives as a Unity asset inside a 39 MB data.unity3d rather than as recognisable MAME set files.

03Getting in: the loader was hiding in plain sight

Allwinner SoCs have a boot ROM mode called FEL that speaks a simple USB protocol and gives you arbitrary memory read, write and execute. The question was how to enter it, and which port.

The answer, from the vendor's own instructions: hold the pinhole Programming button, then insert USB-C into the rear power jack. The power port is also a data port. Release after about five seconds.

$ sunxi-fel version
AWUSBFEX soc=00001890(A523) 00000001 ver=0001 44 08 scratchpad=00061500

soc=0x1890 independently confirmed the sun55iw3 identification that had come from a factory boot log — this time from the live device rather than from a file.

Learned the hard way

Reading an unmapped address over FEL hangs the endpoint. I tried 0x100000; the device stayed enumerated but every subsequent bulk transfer timed out, and only a physical replug cleared it. Stay inside SRAM until DRAM is up. This costs you a replug cycle every time you guess wrong, which is a strong argument for deriving addresses rather than trying them.

04Writing our own flasher

FEL alone is not enough to read the flash. The boot ROM has no storage driver at all — it cannot touch eMMC. To read partitions you have to bring up DRAM and a storage stack first, which is what Allwinner's second-stage FES protocol is for:

FEL  →  load fes1.fex into SRAM, run it       (initialises DRAM)
     →  load u-boot.fex into DRAM, run it     (enters "efex" mode)
FES  →  partition read/write commands

I derived the command set from two independent sources that had to agree: the strings in the device's own u-boot.fex (FEX_CMD_fes_up, fes_down, fes_force_erase…) and the numeric opcodes in FELix. Every name in FELix's enum appears in this firmware's U-Boot, so the enum is this device's command set.

That mattered more than it sounds, because fes_up (read) and fes_down (write) are adjacent opcodes, and force_erase sits in the same table. Getting one digit wrong is the difference between a backup and a brick.

Design decision

So the dumper is read-only by construction, not by discipline. FES_DOWNLOAD, FES_FORCE_ERASE and FES_FORCE_ERASE_KEY are not defined anywhere in the file. There is no flag to get wrong and no branch to take by accident; a bug in that tool can only ever produce a bad read.

Writing lives in a separate tool that refuses any sector whose current contents match neither the recorded original nor the intended result, and reads back and compares everything it writes.

The bug that would have ruined the backup

The first full dump completed cleanly and produced 27 files that all looked plausible. They were entirely wrong.

The GPT's logical block addresses sit 40960 sectors above where FES actually addresses data. Every partition had been read from 20 MiB past where it should have been. The file named private.img actually contained media_data. Nothing errored, nothing looked corrupt, and every file was exactly the right size.

What caught it was checking filesystem magic numbers rather than trusting the sizes. The fix is a calibration pass that probes known-signature partitions before dumping anything:

probes = [("boot_a",        b"ANDROID!"),
          ("init_boot_a",   b"ANDROID!"),
          ("vendor_boot_a", b"VNDRBOOT"),
          ("vbmeta_a",      b"AVB0")]

for offset in (40960, 0):
    ...
sys.exit("could not calibrate FES addressing — refusing to dump")

If it cannot prove which addressing scheme it is talking to, it refuses to run. A backup you cannot verify is not a backup.

The resulting 27-partition dump captured something that exists nowhere else: this unit's factory firmware, which is older than anything the vendor publishes. The public download only overwrites eleven partitions; the per-device material — the keybox, the frp partition explicitly preserved across re-production — sits outside that write set.

No secure boot. Anywhere.

Worth stating plainly, because it is the reason any of the rest was possible: the secure boot fuse is clear, the AVB flags are zero, and there is no dm-verity. The only integrity check anywhere in the update path is a 32-bit sum of words.

05The real problem: nothing could be observed

At this point I could read and write flash, and had a verified backup. What I did not have was any way to see what the device was doing. FES gives you no console output. The console has no network. The HDMI output showed a kiosk that did not care what I had patched.

I applied five separate property patches to enable adb over several rounds. Every one of them was written correctly, verified by read-back, and produced absolutely no observable change. Five rounds of a completely blind loop.

The way out was to stop trying to fix the problem and instead build a feedback channel. The U-Boot splash screen lives as a bitmap in a FAT16 filesystem inside the bootloader_a partition — so I replaced it.

06Then we opened it, and found a labelled UART

Three unpopulated headers sit along the right edge of the board, all clearly silkscreened:

On the solder side, SW1 is silkscreened FEL — the pinhole programming button, named for exactly what it does — and SW2 is AP-RESET. The USB-C power port is silkscreened POWIN.

Three things fell out of that immediately. enable_jtag is printed by BOOT0, so the JTAG header is live rather than fused off. 59640 MB independently corroborated the eMMC size measured over FES. And the boot chain is BOOT0 → BL31 → SCP → U-Boot, which explains why a bare u-boot.fex is only part of the story.

macOS gotcha that will cost you an evening

termios settings on /dev/cu.* evaporate when the last file descriptor closes. Running stty -f /dev/cu.X 115200 and then cat /dev/cu.X as two separate processes silently reverts to 9600 baud — I verified this by re-opening immediately after setting it. The port must be held open across both the configure and the read. A naive stty && cat one-liner hands you garbage that looks exactly like a wiring fault.

07The adb bug was mine

With a root shell on the serial console, one logcat explained five rounds of failure:

avc: denied { setcurrent } for scontext=u:r:adbd:s0 tcontext=u:r:adbd:s0 permissive=0
adbd: main.cpp:162] Could not set SELinux context

ro.secure=0 was the thing breaking adb — and I had set it myself, in the very first patch, to loosen security.

Here is the mechanism. With ro.secure clear, should_drop_privileges() returns false, so adbd tries to stay root and calls selinux_android_setcon(u:r:su:s0). A user build's policy contains no such transition. The kernel denies setcurrent, adbd hits a LOG(FATAL), and restarts every five seconds, forever.

Everything else had been correct the whole time. The UDC was present as 4100000.udc-controller, functionfs was mounted, and all five properties had applied exactly as written. The single patch intended to make the device more open was the one preventing it from opening.

$ adb shell getprop ro.product.model
A527 PRO

There is a wider lesson in that, and it is not about Android. Five rounds of blind patching produced five rounds of nothing, and the fix took one line of log. The expensive part of the project was never the crypto or the flash protocol — it was working without feedback. Building the observation channel should have come first.

Confirmed surviving a reboot. The console now boots to a general-purpose Android UI, and the original software launches on purpose rather than by default.

Part two

The gun

The console was the harder target. The gun turned out to be the more interesting one — and, for anyone who just wants a cheap light gun, by far the more useful.

09Five interfaces, and one of them is a gift

GAIME v1 — Tassei Denki Co.,Ltd — VID 0x2E2C  PID 0x0631
bcdDevice 0x0419, serial 9165, USB 2.0, 500 mA
bDeviceClass 0xEF / sub 2 / proto 1   (composite, interface association)
#ClassWhat it is
0HIDBoot keyboard, 8-byte reports
1HIDDigitizer — the pointer
2HIDVendor page 0xFF00, 64-byte in/out — config
3VideoUVC VideoControl
4VideoUVC VideoStreaming

Interface 1 decodes to this:

Usage Page (Digitizer) / Usage (Touch Screen), Report ID 1
  Tip Switch    1 bit     <- trigger
  In Range      1 bit     <- gun claims it has screen lock
  padding       6 bits
  X, Y          16 bits each, Logical/Physical 0..10000, Input(Data,Var,Abs)

A six-byte report, and X and Y are absolute over a normalised 0–10000 space. That is precisely what light gun use requires, and it is why the gun works as a no-calibration absolute pointer the moment you plug it into any PC.

It also settles the biggest open question about the product. All of the computer vision runs inside the gun. The console has no camera hardware whatsoever, and the gun reports derived coordinates while accepting calibration coefficients back. For pointing purposes the console is entirely optional — which means this is, functionally, a Sinden-class light gun at a third of a Sinden's price.

10Measuring the jitter everyone complains about

Reviews of this product mention the pointer jumping on trigger pull. Having a decoder meant I could measure it rather than speculate. Ten seconds of capture with the gun sitting on a desk, not aimed at a display:

Report rate~278 Hz in one capture, ~28 Hz in another — wildly variable
X / Y range99 … 9900 (the full span it will produce)
Mean jump|dX| 93.5, |dY| 86.6 counts per report
Worst jump4841 counts — about half the screen, in one report
in_rangeset in 2781 of 2781 reports, while producing all of the above

Two things matter there. First, the descriptor declares 0–10000 but the gun clamps to 99–9900, so that is the range you should actually map to screen coordinates.

Second — and this corrected a guess I had made confidently in writing — the in_range bit is asserted continuously even while the output is garbage. I had assumed it would make a clean validity gate, a free "do I see the screen" signal. It is useless for that. It never once cleared, across 2781 consecutive reports of pure noise.

With no screen lock the gun does not jitter gently around a point; it sweeps the entire coordinate space. For an absolute pointer at up to 278 Hz, that means the cursor gets teleported hundreds of times a second, and your desktop becomes unusable — which is exactly the reported symptom, now with numbers attached.

So the filtering has to be geometric rather than flag-based: a median-of-5 spike filter plus a maximum-jump gate, with a run of six consecutive "outliers" accepted anyway so that genuinely fast aiming still tracks.

Not wrecking your desktop in the meantime

macOS matches interface 1 as a system pointing device, so simply plugging the gun in hijacks your cursor. gun_bridge.swift seizes the digitizer with kIOHIDOptionsTypeSeizeDevice, which stops macOS routing it anywhere:

work/gun_bridge --log              # seize + print reports
work/gun_bridge --block            # seize + swallow everything
work/gun_bridge --app RetroArch    # forward only while RetroArch is frontmost

Start it before plugging the gun in — it waits for the device and grabs it on arrival, so the cursor is never hijacked at all. This also explained an earlier dead end where raw HID reads returned nothing: macOS had the device open and would not share it.

11Talking to the gun directly

Interface 2 carries the vendor's config protocol in 64-byte reports. The console-side methods are named encrypt*, but there is no encryption — it is framing plus a Modbus CRC-16, little-endian, over the leading N bytes:

byte 0     function code      5 = SYSTEM_CMD
byte 1     data length        1 = gun mode, 33 = calibration
byte 2     sub-function       5 = gun mode, 6 = calibration, 7 = MD5 result
byte 3-5   reserved (zero)
byte 6     payload / flags
byte 7+    payload
last 2     Modbus CRC-16, little-endian

Verified against the real gun, with no console involved anywhere:

$ python3 tools/gun_probe.py gunmode 0
hid_write returned 65  error='Success'
packet: 05 01 05 00 00 00 00 83 d1 …
reply:  05 01 05 00 00 00 01 42 11 …

The gun accepts the command and returns a well-formed 64-byte acknowledgement: same function code, same sub-function, and a valid Modbus CRC-16 (0x1142, checked independently). A host can drive this gun today, with no vendor software — single-shot versus autofire, the calibration grid, and the black/white/pink screen-edge assist bars added in firmware v4.0.3.

One sub-function is more interesting than the others. Number 7 returns a bit-packed MD5 validation result to the gun, which is almost certainly the accessory check added in v4.0.3 — an anti-counterfeit handshake.

12The camera stream is a test pattern

The gun presents its camera to any host as a standard UVC device, "Dashine UVC", with a sensible-looking mode list up to 1920×1080. Capturing it seemed like the fastest route to understanding the tracking.

{{FIG:gunfeed}}

What comes out is not imagery. It is a synthetic scrolling gradient, and the measurements are unambiguous:

  • Every row is perfectly uniform horizontally — per-row standard deviation across x is exactly 0.000 in all three channels. No lens and no sensor can do that.
  • R and B clip to 0 or 255 together while G ramps linearly at ~0.418 per row.
  • The pattern scrolls vertically at exactly +1.6 rows per frame, perfectly linear across 60 frames.
  • Zero sensor noise. Frame 0 rolled by 8 rows is bit-identical to frame 5; rolled by 16 rows it is bit-identical to frame 10. Max difference: 0. A real sensor always shows read noise.

So the UVC bridge enumerates, negotiates a format and streams happily, but the sensor pipeline behind it is not in imaging mode. What you get is a built-in ramp test pattern.

This looks like a bring-up leftover that shipped disabled rather than a fault. Nothing in the console-side code ever touches video — across the service, the calibration app and the launcher there are only three sub-function codes and no camera or video command of any kind. The console has no camera hardware and never consumes a video stream.

Read this one carefully

The vendor's own string descriptor for interface 4 reads "Video Inactive", which is tempting to quote as proof. It isn't. In UVC, alt setting 0 of a streaming interface is conventionally the zero-bandwidth "inactive" alt, and interface 4 does report bNumEndpoints = 0 at alt 0 — so the string may just be labelling that. Suggestive, not conclusive. The pixel measurements above are the load-bearing evidence.

13Opening the gun

No public teardown of this device existed, so all of this is new.

{{FIG:gun_open}}

The main board is LBQ-1585-C-V1.1, dated 2025-07-23, with a trigger daughterboard LBQ-1585-D-V1.1. And the board number gives something away: PID 0x0631 is 1585 decimal. The USB product ID was assigned straight from the internal project number, which is a useful handle for searching supplier and FCC databases.

{{FIG:gun_soc}}

Two things dominate that photo. J3 is four unpopulated plated through-holes, silkscreened GND / TX / RX / V3.3 — a serial console, with a square pad on the reverse marking pin 1. And the large central IC at U8 is a ~96-pin QFN whose top is completely blank at full magnification. No laser etch, no logo, nothing. House-marked or deliberately unmarked.

Which means the SoC cannot be identified from the package at all. It has to come from a UART boot log. That one fact makes J3 the whole ballgame.

{{FIG:gun_back}}

The back is nearly bare — a couple of tactile switches, some 0402 passives, no debug header beyond J3, and critically no DRAM and no second flash. Combined with the front, that settles the architecture: the boot medium is a single GigaDevice SPI NAND (1 Gbit / 128 MiB, 1.8 V, WSON-8) near the camera end, and the DRAM must be stacked in-package with the SoC.

A ~1 GB system-in-package with in-package DDR plus 128 MiB of SPI NAND is a coherent, conventional design for a Linux-class vision part — and it matches the vendor's own published claim that each gun runs Linux with 1 GB of RAM and a 1080p camera in the barrel.

{{FIG:gun_camera}}
Correction

An earlier version of my notes said "an SPI-NOR chip in an SOIC-8 can be read in place with a clip." Both halves of that are wrong for this board. It is NAND, not NOR — a bare CH341A with flashrom will not touch it, since flashrom does not do SPI NAND. And it is WSON-8, not SOIC-8: the pads are underneath the package, so a SOIC clip physically cannot attach.

That inverts the plan. Get UART first, reach a shell or interrupt the bootloader, and dump the NAND in-circuit through the SoC. Desoldering becomes the fallback, not the opening move.

14Can the gun be reflashed? Not through any visible path

I checked this from every angle available without opening it, and the answer is consistently no.

The gun exposes no update interface. One USB configuration, no alternate config hiding anything, five interfaces that are three HID and two Video. There is no DFU interface (class 0xFE/subclass 0x01) and no vendor-class interface (class 0xFF). There is nothing to flash into.

The console never updates the gun. No gun firmware blob exists anywhere in any SKU's image — searching all of system, vendor and product for *.bin, *fw*, *firmware*, *.hex, *.dfu and *gun* turns up only stock Allwinner BSP leftovers. And no code references one: grepping the service, the calibration app and the launcher for bootloader, dfu, upgrade, updateFirmware and gunVersion returns zero hits.

The gun's version appears only as bcdDevice = 0x0419, independent of the console's version space. It looks factory-programmed only.

That leaves two plausible routes, neither yet attempted: a bootloader entered by a button-or-trigger combo held while plugging in (common on this class of device, invisible from descriptors, and cheap to test), or an undocumented sub-function beyond 7 on interface 2. Do not blind-scan the latter. Firing unknown function codes at a device with a writable loader is exactly how a unit becomes a paperweight — derive it from the gun's own firmware first, which means getting that UART working.

15What's still open

The gun's SoC is unidentified. Everything downstream — its firmware, the CV pipeline, whether the camera can be put into imaging mode — waits on soldering three wires to J3 and reading the boot log.

adb is not yet permanent. The fix is a genuine one-byte revert of ro.secure=0 back to 1 at a known sector, keeping ro.debuggable=1 so the serial console survives. Until then setprop service.adb.root 0 has to be re-applied over serial after each boot. The write needs FEL, and the FEL button snapped off during disassembly — it is a momentary switch, so briefly shorting its own pads does the same job.

There is no mouse cursor. Plug a USB mouse into the front port and it works — the device enumerates correctly (Classes: CURSOR | EXTERNAL, Mode: POINTER), motion tracks, clicks land where you aim. There is simply no arrow drawn. The obvious theory was that the vendor blanked the pointer artwork, since the games draw their own crosshair, but that is disproved: the pointer bitmaps in framework-res.apk are intact and fully opaque. The current lead is that SurfaceFlinger has no Sprite layer at all, meaning the cursor surface is never created in the first place.

The System 22 core's debug hooks are exported and untouched, and the ROM data sits inside a Unity asset bundle rather than as loose files.

A note on what this is and isn't

This is documentation of a device I bought, using a firmware image its manufacturer publishes to anyone who asks. No game data is redistributed here and none will be. The full flash backup exists so that this unit can be restored, and it stays on my disk — it contains a complete copy of licensed commercial software.

Device-unique identifiers — the chip SID, the adb serial derived from it, eFuse contents — are redacted throughout the published notes. The raw teardown photographs carried GPS EXIF with precise coordinates and are not committed; every image on this page comes from a stripped copy.

If you own one of these and want to follow along: the read-only paths are genuinely safe, and the write paths are genuinely not. Take the backup first, and make sure you can prove it is a real backup before you rely on it. Mine wasn't, the first time.
